# GeoPulse Attendance API Contract

The React/Vite client does not contain a Prisma client and does not write official attendance rows directly. Configure `VITE_ATTENDANCE_API_URL` to the separately hosted backend API. The API must validate every request independently; client-side geofence results are informational only.

All protected endpoints require `Authorization: Bearer <Supabase access token>` and must validate the token with Supabase Auth. Do not expose `DATABASE_URL`, Prisma credentials, or a Supabase `service_role` key to the client.

`GET /api/health` is public and returns only `{ "status": "ok", "service": "geopulse-attendance-api" }`; it does not reveal database or credential state.

## Active Work Location

`GET /api/work-locations/active`

Success response (`200`):

```json
{
  "id": "work-location-uuid",
  "name": "Office name",
  "latitude": -6.2,
  "longitude": 106.8,
  "radiusMeters": 100,
  "maxAccuracyMeters": 20,
  "isActive": true
}
```

Return `404` when there is no active work location. Coordinates and radius must come from backend configuration. `maxAccuracyMeters` is required for client-side preliminary geofence validation; the server must apply the authoritative configured limit as well.

## Check In / Check Out

`POST /api/attendance/check-in`

`POST /api/attendance/check-out`

Request body is `multipart/form-data`. The location fields remain unchanged and a
confirmed `photo` part is required:

| Field | Value |
|---|---|
| `latitude` | GPS latitude |
| `longitude` | GPS longitude |
| `accuracy` | GPS accuracy in meters |
| `timestamp` | ISO timestamp from the GPS reading |
| `workLocationId` | Active work-location UUID |
| `photo` | Confirmed JPEG selfie, maximum 5 MB |

The photo must have a valid JPEG signature and is uploaded to the private
`ATTENDANCE_PHOTO_BUCKET` before an attendance row is committed. A failed upload
must fail the attendance request. The client timestamp is untrusted and must not
determine the official attendance time. Use server time. The server must validate
the authenticated employee, active account, coordinates, GPS accuracy policy,
active work location, geofence radius, attendance rules, duplicate check-in/out,
and current attendance state.
The JSON-only attendance request format is no longer accepted; deploy the updated
client and API together so photo-less requests cannot create attendance.

Successful response (`200` or `201`) must include the server-verified row:

```json
{
  "id": "attendance-uuid",
  "employee_id": "employee-uuid",
  "type": "check_in",
  "attendance_date": "2026-10-19",
  "checked_at": "2026-10-19T02:00:04.000Z",
  "latitude": -6.2,
  "longitude": 106.8,
  "gps_accuracy_m": 12,
  "distance_to_office_m": 35,
  "is_within_geofence": true,
  "office_id": "work-location-uuid",
  "verification_status": "verified",
  "photo_captured_at": "2026-10-19T02:00:04.000Z"
}
```

The client treats the request as successful only when `verification_status` is `verified`, `is_within_geofence` is `true`, and `office_id` matches the submitted work location. All validation failures must return a non-2xx response with a JSON `message`; never return a success-shaped response when the attendance was not approved.

## Admin Attendance Photo Evidence

`GET /api/admin/attendance-photos?limit=50` requires a verified bearer token and
an active employee whose `employees.role` is `admin`. It returns only attendance
records with photo evidence, including the employee ID, check-in/check-out type,
server-recorded photo acceptance timestamp, GPS fields, and a private signed
photo URL that expires after five minutes. The timestamp is generated by the API,
not trusted from the client. The endpoint and Storage RLS policies reject
non-admin access. Employees can access only their own private photo objects.

## Attendance History

`GET /api/attendance/history?limit=30` returns the same attendance row shape as the successful write response in descending attendance-date/check time order. It is optional for the current UI, which still renders its passed-in records, but is available for replacing local history data. The server always derives the employee from the verified token and does not accept an employee ID query parameter. Errors use `{ "error": "stable_code", "message": "Human-readable explanation" }`.

## Local And Mobile Testing

- `localhost` is a secure context for browser geolocation during local development.
- Camera access also requires HTTPS (except localhost) and is requested only after the employee explicitly starts check-in or check-out.
- To test on a phone, expose the development site over HTTPS or use an HTTPS tunnel. Plain HTTP on a LAN IP is not generally a secure context.
- Grant location permission in the browser. A denied permission must be changed in the browser's site settings; the web app cannot open OS settings directly.
- Mobile browsers can pause location updates when the tab is backgrounded or the screen is locked. This web client pauses its watcher while hidden and restarts it when visible.
- A real device test is still needed to verify GPS quality and browser-specific permission behavior.
